# 운영 안내

운영 서버(Cloudtype)를 확인하고 문제를 짚을 때 보는 문서. 변경 이력은 `CHANGELOG.md`, 이유와 측정 근거는 `작업기록/`.
비밀 값(API 키)은 이 문서에 적지 않는다. 키는 Cloudtype 환경변수와 로컬 `.env`에만 둔다.

## 1. 구조 한눈에 (질의응답 경로)

```
[첫 질의응답] POST /api/analyze/other_review  →  job_id  →  (백그라운드 스레드 run_other_review)
   법령·고시명 추출(Gemini flash, 병렬) → 법제처 원문 조회(법령 조문 + 고시 조문·별표) → 본 답변(Gemini pro)
   → 링크 교정(law_linkify) → 서버 인용 검증(citation_check) → 시행일 푸터
   결과는 GET /api/analyze/other_review_status/<job_id> 로 받는다
[후속 질문]   POST /api/chat/other_review      →  바로 응답(동기, 30초 안에 끝나야 함)
   qa_grounding이 새 질문에 맞춰 고시·법령을 다시 발췌해 근거로 첨부 → Gemini pro(사고 예산 512) → 같은 후처리
```

- 모든 Gemini 호출은 `gemini_client.py`를 거친다(구 SDK 없음).
- 서버는 `gunicorn app:app`이고 `gunicorn.conf.py`(자동 적용)로 **워커 1개 + 스레드 8개(gthread), 제한 120초**다. 예전엔 워커 1개 동기 방식이라 요청이 한 번에 하나씩만 처리됐고, 법정 의무 마스터가 5개를 동시에 보내면 일부가 줄을 서다 Cloudtype 게이트웨이 제한(60초)에 걸려 504가 났다. 워커를 늘리지 않는 이유는 아래 메모리 때문이다. 작업 목록(`JOBS`)과 후속 채팅 기억(`qa_grounding`)은 서버 메모리라 **재시작·강제 종료 시 사라진다.**
- 완료된 작업은 상태 경로로 **한 번 읽으면 삭제**된다(두 상태 경로 모두). 같은 `job_id`를 두 번 읽지 않는다.

## 2. 설정 스위치 (환경변수)

Cloudtype 환경변수를 바꾸면 **서버를 재시작해야 반영**된다.

| 변수 | 기본값 | 용도 | 되돌리기/조정 |
|---|---|---|---|
| `GEMINI_API_KEY` | (필수) | Gemini 호출 | 없으면 AI 기능이 오류를 낸다 |
| `GEMINI_MAIN_MODEL` | `gemini-2.5-pro` | 본 답변·후속 질문 모델 | 모델 종료 공지가 나오면 새 이름으로 |
| `GEMINI_FAST_MODEL` | `gemini-2.5-flash` | 법령명 추출·인용 판정 등 가벼운 호출 | 위와 같음 |
| `GEMINI_MAIN_FALLBACKS` | `<MAIN>,<FAST>` | 본 답변 실패(한도 초과 등) 시 순서대로 시도할 모델(쉼표) | |
| `CITATION_VERIFY_MODE` | `off` | 구글검색 인용 검증 패스(질의응답 경로만): `off` / `pro` / `flash` | 서버 검증만으로 부족하다고 느끼면 `pro` (약 +40초). `flash`는 손상 위험이 있어 권하지 않는다 |
| `LAW_BYEOLPYO_IN_ANSWER` | (켜짐) | 첫 질의응답 근거에 법·시행령·**시행규칙**과 질문 관련 별표(최대 2개)를 넣는다 | `0`이면 끈다(법·시행령 조문만, 예전 동작). 법제처 컨텍스트 단계가 약 6~15초 늘고 프롬프트가 커진다 |
| `MOLEG_API_KEY` | 코드 기본값 | 법제처 API | 법제처가 막히면 확인 |
| `SKIP_ONLINE_TESTS` | (없음) | 테스트에서 법제처 접속 테스트 건너뛰기(`1`) | 자동 점검이 사용 |

설계도서 검토는 이 스위치와 무관하게 구글검색 검증 패스를 유지한다(`app.py`).

> **법정 의무 마스터 동시 요청 수**: 화면(`duty_list.html`의 `CONCURRENCY`)은 파트를 6개씩 동시에 보낸다. 서버 스레드(`gunicorn.conf.py`의 `threads=8`)보다 작게 둬서 다른 요청이 낄 자리를 남긴다.
> 올리려면 두 값을 함께 올리고(예: 스레드 16·동시 8~10), 먼저 Gemini 호출 한도(429)를 확인한다. 한도를 넘으면 파트가 실패해 화면에 경고가 뜬다.

## 3. 배포 후 확인 절차

푸시 확인 → 배포 → 아래 순서로 본다. 푸시는 반드시 원격 해시로 확인한다: `git ls-remote origin refs/heads/main`이 로컬 `git rev-parse HEAD`와 같아야 한다.

1. **서버 기동**: 운영 주소 `/`와 `/other_review`가 200. 배포 직후 1~2분은 전 경로가 Cloudtype 404일 수 있다(컨테이너 교체 중). 계속되면 Cloudtype 빌드 로그를 본다(보통 `requirements.txt` 설치 오류).
2. **첫 질의응답**: 아래 질문을 `POST /api/analyze/other_review`에 보내 완료까지 기다린다. 소요 85~110초가 정상 범위.
   - 질문: `건설사업관리 인원수 산정할때 기술지원인수를 산정하지 않아도 문제가없어?`
   - 기대: 「건설엔지니어링 대가 등에 관한 기준」 **제9조 제1항**과 **별표 2 바목(단순 10%·보통 15%·복잡 20%)** 인용, `law.go.kr/행정규칙/` 링크, 답변 끝 **"참고한 고시·지침의 현행 정보" 푸터**(시행일은 고시가 개정되면 달라진다. 2026-11 기준 대가기준 2023-10-17, 업무수행지침 2026-07-08), ⚠️ 없음, `(정확한 근거 조항 확인 필요)` 없음.
3. **후속 질문** (`initial_context`는 2번의 `other_review_status` 응답에서 받은 값을 그대로, 프론트와 같은 방식). **각각 15~20초, 30초 미만**이어야 한다.
   - `기술지원기술인 비율은 몇 퍼센트로 산정해? 발주청이 협의해서 정하는 거야?` → 10/15/20% 인용 + "원문에는 협의한다는 내용이 없다"
   - `토목공사에서 공종이 단순한지 보통인지 복잡한지는 어떻게 구분해? 하천제방 공사는 어디에 해당해?` → 별표 2 사목 구분표, 하천제방은 단순한 공종
   - `낙찰률이 정확히 60%로 낙찰됐는데 시공단계 건설사업관리기술인을 추가 배치해야 해? 몇 퍼센트 추가야?` → 단정하지 않고 "원문이 이 경우를 명시하지 않아 확인 필요"
   - 답변이 최초 질문(산정 제외 가능 여부)부터 다시 시작하면 안 된다.
4. **새 고시 힌트**: `콘크리트 품질시험 횟수는 어떻게 정하고, 안전관리계획서 수립 대상은 어떻게 되나요?` → 푸터에 건설공사 안전관리 업무수행 지침과 건설공사 품질관리 업무지침.
5. 확인되면 `CHANGELOG.md`의 상태를 ✅로 바꾸고, 상위 저장소 포인터를 갱신(§7).

## 4. 로그에서 볼 줄 (Cloudtype 로그)

| 줄 | 의미 |
|---|---|
| `[gemini] 라벨 model=… 12.3s in=… out=… think=…` | Gemini 호출 1건의 모델·시간·토큰. 어느 모델이 답했는지, 어느 호출이 느린지 |
| `[gemini] 라벨 model=… 실패: …` | 해당 모델 실패 → 다음 모델로 폴백. 연속 실패면 한도 초과/키 문제 |
| `[run_other_review] 단계별 소요(초): {…} / 합계 N` | 첫 질의응답 단계별 시간(준비, 법제처 컨텍스트, 본 답변, 검증 패스, 후처리) |
| `[의무 추출] 파트 n: 결과가 없는 조 […] 재검토` | 1차 추출에서 의무 표현이 있는 조가 0건이라 그 조만 다시 물음. 잦으면 프롬프트·모델을 의심 |
| `[의무 추출] JSON 해석 실패(시도 n/2)` | 법정 의무 마스터에서 모델 응답이 깨짐. 2번 다 실패하면 화면에 "N개 파트 분석 실패" 경고와 재시도 버튼이 뜬다 |
| `[qa_grounding] … 건너뜁니다/실패(무시)` | 후속 채팅 근거 조회가 12초를 넘거나 실패 → 근거 없이 답함(품질 저하, 오류는 아님) |
| `[citation_check] 판정 호출 실패(원문 유지)` | 인용 주제 판정 LLM 실패 → 판정 없이 존재·수치 검사만 적용 |
| `[moleg_mcp] law.go.kr 호출 실패 …` | 법제처 API 접속 문제 |
| `[mcp_agent_sync] … extraction failed` | 법령·고시명 추출 LLM 실패 → 낱말 힌트로 대체 |

## 5. 문제가 생겼을 때

| 증상 | 먼저 볼 것 | 원인 후보와 조치 |
|---|---|---|
| 전 경로 404(Cloudtype 페이지) | 배포 시각, Cloudtype 빌드 로그 | 교체 중이면 1~2분 대기. 계속되면 빌드 오류(의존성 설치). 직전 정상 빌드로 되돌린다 |
| 답변이 조문 번호·수치 없이 일반론 | 로그의 `[moleg_mcp]` 오류, 답변 끝 푸터 유무 | 법제처 접속 실패, 고시 이름 변경·폐지(힌트 테스트 실패), 질문에 힌트 낱말이 없고 LLM이 이름을 못 뽑음 → `_ADMRUL_HINTS`에 낱말 추가 |
| 후속 질문이 실패하거나 서버가 갑자기 초기화 | 후속 질문 응답 시간, 로그의 워커 재시작 | 30초 초과로 워커 강제 종료 → `JOBS`·기억 소실. 근거 조회 지연/모델 지연 확인, 사고 예산 낮추기, 필요하면 `Procfile`에 `--timeout` 추가 검토 |
| 후속 답변에 원문에 없는 말이 섞임 | `[qa_grounding]` 로그(근거가 붙었나) | 서버 재시작으로 기억이 사라져 힌트 고시만 사용됨 / 근거 조회 지연으로 생략됨 |
| 정확한 인용에 ⚠️·💡가 붙음(오탐) | 해당 줄의 경고 문구 | ⚠️ 원문 불일치 = 주제 판정 LLM, 💡 비율 = 문장 속 %가 원문에 없음, 💡 용어 = 인용 뒤 따옴표 용어가 조문에 없음. 재현해서 `citation_check.py`와 테스트를 보강 |
| 틀린 인용이 경고 없이 통과 | 링크 형식 | 링크로 인식되지 않으면 검증 대상이 아니다. 필요하면 `CITATION_VERIFY_MODE=pro` |
| 429·한도 초과 | `[gemini] … 실패` | flash로 폴백되는지 확인, 키 한도 |
| 특정 고시가 안 붙음 | 법제처에서 이름·현행 여부 | `python -c "import moleg_mcp as m; print(m._lookup_admrul('고시명'))"` (정확히 일치하는 현행본만 사용) |

### 변경을 되돌릴 때
- 설정으로 되돌리기: §2 표의 환경변수 + 재시작(코드 배포 불필요).
- 코드로 되돌리기: `git revert <커밋>` → 푸시 → 배포 → §3. 되돌릴 대상은 `CHANGELOG.md`에서 찾는다.

## 6. 테스트

```bash
cd backend
python test_admrul.py                 # 고시 조회·인용 검증·후속 근거 (법제처 접속 테스트 포함)
python test_gemini_endpoints.py       # 엔드포인트가 Gemini에 넘기는 모델·형식·설정 (가짜 Gemini, 접속 불필요)
python test_duty_text.py              # 법정 의무 마스터: 본문 파싱·조각·조 번호 대조·채팅 (실제 법령 1건 접속 테스트 포함)
python test_award.py                  # 적격심사 종합평점(award_engine)·원문 숫자 대조(award_check, 법제처 PDF 1건 접속 테스트 포함)

```

- `test_admrul.py`의 온라인 테스트는 고시 원문에 의존한다. **고시가 개정돼 문구가 바뀌면 실패할 수 있다.** 그때는 원문을 확인하고 기대 문구를 갱신한다.
- 법제처에 연결되지 않으면 온라인 테스트는 자동으로 건너뛴다.
- `test_award.py`의 온라인 테스트(`AwardCheckOnlineTests`)는 낙찰자 결정기준 현행 PDF(약 5MB)를 받아 명세 숫자 26개를 대조한다. **예규가 개정돼 그 숫자가 바뀌면 일부러 실패한다**(§10 대응).

## 7. 푸시·배포·포인터 절차

1. `backend`에서 커밋 → `git push origin main` → **`git ls-remote origin refs/heads/main`으로 원격 해시 확인**(푸시가 안 올라가 있던 적이 있다). 거부되면(봇 커밋) `git pull --rebase origin main` 후 재푸시. 리베이스하면 커밋 번호가 바뀐다.
2. Cloudtype에서 새 빌드 확인(자동 배포가 아니면 수동 재배포).
3. 배포 후 §3 확인.
4. 상위 저장소(`kshantigravity`): `git add backend` → 커밋(`backend <이전> -> <새>`) → 푸시. `.github/workflows/law_crawler.yml` 삭제처럼 `backend`와 무관한 변경은 같이 커밋하지 않는다.

## 8. 의존성 정기 점검(Dependency Canary)

- 매일 06:00(KST) GitHub Actions가 `requirements.txt` 그대로 **최신 버전**을 설치해 테스트를 돌린다(`.github/workflows/dependency_canary.yml`). 서버 배포에는 영향 없음.
- 깨지거나 `google-genai` 큰 버전이 `TESTED_MAJOR`(현재 2)를 넘으면 `dependency-canary` 이슈가 **하나만** 열린다. 이슈에 설치된 버전 목록과 실행 로그 링크가 있다.
- 대응: 로그에서 실패 단계 확인 → 지금 배포하면 깨질 수 있으니 `requirements.txt`에 상한선(예: `google-genai>=2.24,<3`)으로 임시 차단하거나, 새 버전을 로컬에서 테스트하고 실제 호출을 확인한 뒤 워크플로의 `TESTED_MAJOR`를 올린다. 해결되면 **이슈를 닫는다**(닫혀야 다음 실패에 새 이슈가 열린다).
- 이슈 생성 단계는 실제 실패로 시험한 적이 없다(첫 실패가 첫 시험).

## 9. 고시 힌트 추가·수정

`mcp_agent_sync.py`의 `_ADMRUL_HINTS`에 `(질문 속 낱말들, [고시 정식명])`을 추가한다.
- 고시명은 법제처 정식 이름과 **한 글자도 다르지 않게**(접두어 `(계약예규)` 포함). `test_every_hinted_name_exists_in_moleg_as_an_exact_current_match`가 현행·정확 일치를 확인한다.
- 낱말은 해당 업무에서만 쓰는 말로(너무 흔한 말은 관련 없는 질문에도 붙는다). 목록 앞쪽이 우선이고 한 질문에 최대 3개.

## 10. 적격심사(낙찰자 결정기준) 명세와 개정 대응

사업수행능력평가 점수 산정 화면(`/pq_score`)의 **6단계 "적격심사 통과 기준 계산"**(`static/award_panel.js`)은 용역비(추정가격·예정가격)와 PQ 점수(5단계 결과가 자동으로 들어오거나 직접 입력)로 **"입찰가격을 얼마로 써야 적격심사를 통과하는지"를 거꾸로 계산**한다(`award_reverse.py`, `/api/award/required_price`). 근거는 「지방자치단체 입찰시 낙찰자 결정기준」(행정안전부 예규)의 **제2장의2 [별표 1] 사업수행능력평가(P.Q)를 하는 기술용역** 적격심사다. 접힌 "(참고)" 영역은 반대로 입찰가격이 정해진 뒤 종합평점·낙찰자를 확인한다(`award_engine.py`). 예전 `/award` 주소는 이 화면으로 안내된다.
규정 값(적격통과점수 92·95점, PQ 환산 배점 64/44/34, 입찰가격 산식 등)은 코드가 아니라 `award_specs/jibang_jeokgyeok_tech.json`에 조항 번호와 함께 있다.

- **개정 감지**: 매일 새벽 크롤링 워크플로(`law_crawler.yml`)가 `pq_watch.py`를 돌려 이 예규의 법제처 현행 버전 번호(행정규칙일련번호)를 명세의 `source.law_id`와 비교한다. 다르거나, 아직 시행 전인 개정본(시행 예정)이 있으면 GitHub 이슈(`PQ 평가기준 개정 감지 (…)`)가 열린다. 다른 PQ 기준(pq_specs)도 같은 방식이다.
- **숫자 대조**: 이 예규는 법제처가 본문을 주지 않고 PDF로만 제공한다. 개정이 감지되면 워크플로가 새 PDF를 받아 명세의 숫자 26개를 원문과 대조해 이슈에 **"명세 92 → 원문 90"처럼 바뀐 값만** 적는다. 숫자가 모두 같으면 "적격심사 숫자에는 영향이 없어 보입니다"라고 적힌다(이 예규는 물품·공사 등 다른 장의 개정이 잦다). 문장 모양이 바뀌어 못 찾은 값은 "확인 못 함"으로 알려 준다(조용히 통과시키지 않는다).
- **수동 대조**: `python award_check.py`(현행 PDF를 받아 대조), `python award_check.py --pdf 파일.pdf`, `--text 텍스트.txt`. 바뀐 값이 있으면 종료 코드 1.
- **반영 절차**: ① 이슈의 바뀐 값을 원문(링크)으로 확인 → ② `award_specs/jibang_jeokgyeok_tech.json`의 값과 `source`(law_id·issued·effective·issuer)를 새 버전으로 고침 → ③ `test_award.py`의 기대값(문서 예시·경계값)을 고침 → ④ `python test_award.py` 통과 확인 → ⑤ 푸시·배포. 산식의 모양 자체가 바뀌면 `award_engine.py`도 고친다.
- **자동 대조 대상이 아닌 것**: 경영상태 신용평가 점수표(2.0/1.8/1.6/1.4/1.0)는 PDF 표 모양이 불안정해 사람이 확인한다. 적용 범위 밖 기준([별표 2] P.Q를 하지 않는 기술용역, [별표 3] 재난복구, [별표 4] 학술연구, 제7장 협상에 의한 계약)은 아직 계산하지 않는다.
- **로그**: `[PQ 기준 감시] 최신/개정됨/시행 예정 개정 있음 …` 줄과 `::warning::` 줄(GitHub Actions 로그).

## 11. 낙찰가 예측(투찰 추천) 모델

`/bid_predictor`에서 **기초금액을 입력**(공고를 골라 쓰면 A값도 자동)하면 과거 낙찰 사례로 "얼마에 투찰하면 낙찰될 확률이 얼마인가"를 계산한다(`bid_rules.py` 낙찰하한 규정, `bid_model.py` 계산, `bid_sampling.py` 기초금액·A값 조회, `bid_service.py` 화면용 조립). AI는 쓰지 않는다.

- **낙찰하한은 추정이 아니라 예규 값**: 지방자치단체 시설공사 적격심사(추정가격 300억원 미만)는 [별표 1]~[별표 7]의 입찰가격 평점 식과 적격통과점수(100억원 미만 95점, 이상 92점)에서 하한이 정확히 나온다(`award_specs/jibang_gongsa_floor.json`). 가격 외 점수가 만점일 때 (입찰가격−A)÷(예정가격−A)의 하한은 2억~10억원 89.745%, 10억~50억원 88.745%, 50억~100억원 87.495%, 100억~300억원 81.995%. 가격 외 점수를 입력하면(점수가 모자라면) 하한이 올라간다(9.5점 → 89.775%). 추정가격 300억원 이상은 이 규정 밖이라 계산하지 않고 이유를 알려 준다.
- **A값**: 국민연금·건강보험·퇴직공제부금·노인장기요양보험료 + 산업안전보건관리비 + 안전관리비 + 품질관리비(기초금액 자료의 항목). 하한은 예정가격이 아니라 (예정가격−A) 기준이라 A가 하한 가격(원)을 크게 좌우한다. 공고를 선택하면 자동 입력되고, 비우면 과거 공고의 A 비율로 추정(결과에 '추정' 표시).
- **원리**: 사례마다 낙찰자의 비율 (낙찰금액−A)÷(예정가격−A)와 사정률(예정가격÷기초금액)을 구한다. "비율 r로 투찰"이라는 정책에서 사정률은 과거 중앙값으로 가정해 내 투찰가를 만들고, 그 사례의 낙찰하한 이상이면서 실제 낙찰금액보다 낮으면 이긴 것으로 센다. 결과는 **낙찰 / 하한 미달로 탈락 / 하한은 넘었지만 더 낮은 가격에 패배** 세 가지로 나뉜다(합 100%). 목표 확률별로 "그 확률 이상인 가장 높은 가격", 탈락 위험 50/25/10% 이하인 "가장 낮은 가격"을 추천한다.
- **현실적인 기대치**: 소액 공사는 참가업체가 수십~수백 곳이고 낙찰자가 낙찰하한 바로 위(+0.05~0.15%p)에 몰려, 사정률(예정가격)이 개찰 때 ±0.5% 정도 흔들리면 한 가격으로 낙찰될 확률은 한 자릿수~10%대다(도로 공고 6개월 실측: 확률 최고 지점 약 6%, 백테스트 실제 1.7~5%). 이 숫자가 정직한 값이며 화면에도 그대로 표시한다. 개선 여지는 사정률(예정가격) 예측과 하한가 범위 안에서의 가격 선택에 있다.
- **누락 없는 조회(백그라운드 작업)**: 화면은 `/api/analyze/bid_predict/start`·`/api/analyze/bid_backtest/start`로 작업을 시작하고 `/api/analyze/bid_job/<id>`로 진행률("기초금액 조회 53/120건")을 확인한다. 서버가 과거 공고의 기초금액·A값을 **끝까지**(최대 200초) 조회하며, 시간 초과·일시 오류는 여러 번 다시 시도한다. 예전 동기 방식(`/api/analyze/bid_predict`)은 게이트웨이 60초 때문에 25초 안에 못 가져온 사례를 빼서, 운영에서 120건 중 65건이 빠진 채 결과가 나온 적이 있다(2026-11-03 확인). 동기 엔드포인트는 시험·호환용으로만 남겨 두었다.
- **API 호출량·보관**: 분석 1회 최대 120건, 백테스트 최대 170건(운영 서버에서는 건당 수 초). 조회한 값은 서버 메모리와 `backend/bid_base_cache.json`(저장소에는 올리지 않음)에 보관해 **재시작·재배포 후에도** 다시 조회하지 않는다(컨테이너 디스크가 재배포 때 초기화되면 사라짐). 공공데이터포털 **일일 호출 한도**를 쓰므로 한 키로 하루에 수십 번 반복 실행하면 한도 초과(429, 화면에는 "일일 서비스 요청제한 횟수 초과")로 조회가 막힌다 → 한도 초과가 확인되면 다시 시도하지 않고 멈추며, 결과 상단에 **"불완전한 결과"** 경고와 사유가 나온다. 한국시간 자정 이후 다시 시도하면 보관된 값은 건너뛰고 이어서 조회한다.
- **응답 시간**: 분석 약 30~90초(처음 쓰는 검색 조건일수록 오래 걸림), 백테스트 약 40~120초. 진행률이 올라가는 동안은 정상이다. 6분이 지나면 화면이 중단하며, 같은 조건으로 다시 실행하면 가져온 값은 보관되어 있어 이어서 진행된다.
- **계산이 안 될 때**: 기초금액을 확인한 사례가 15건 미만이면 `model_error`에 이유가 나오고, 예전 통계(분포·백분위)는 그대로 나온다. 조회 기간을 늘리거나 조건을 넓힌다.
- **확인 절차(배포 후)**: 키워드 `도로`, 기간 6개월, 기초금액 `157981000`(공고 R26BK01764059의 A값 `9113864`)로 분석 → "추정가격 2억원 미만 → [별표 7], 낙찰하한 89.745%(예정가격 대비 약 90.3%)", 사정률 중앙값으로 가정한 낙찰하한가 약 1.43억원, 확률 최고 지점이 한 자릿수%면 정상. 백테스트는 "방식 / 학습 예상 / 검증 실제" 표가 나온다.
- **규정 개정 감시**: `award_check.py`가 새 예규 PDF에서 [별표 1]~[별표 7]의 입찰가격 식·고정점수 비율·최저평점·적격통과점수 33개를 `jibang_gongsa_floor.json`과 대조한다(`python award_check.py --spec jibang_gongsa_floor`, 개정 감지 시 이슈에 바뀐 값만 기재). 값이 바뀌면 이 명세와 `test_bid_model.py`·`test_award.py`의 기대값을 고친다.
- **사정률은 예측할 수 없다(조사 결과)**: 사정률(예정가격÷기초금액)은 발주기관·시기·규모·참가업체 수와 상관이 없고(기관 차이가 분산의 2.5%, 직전 사례 상관 0.008), 입찰자 추첨의 무작위 분포와 같다. 그래서 기관별·시기별 보정은 넣지 않았다(`docs/작업기록/2026-11-01_낙찰가-예측-개선.md` 타당성 조사).
- **참가업체 수는 예측되지만 낙찰 확률을 올리지 못한다(조사 결과)**: 규모·기관·공고명으로 참가업체 수 구간을 52%(한 구간 이내 91%) 맞히지만, 구간별 최고 낙찰 확률은 1~59곳 7.5%, 60~119곳 7.1%, 120곳 이상 5.6%로 표본 오차 안이다. 그래서 공고 선별 기능은 넣지 않았다. 화면의 구간별 표(구간당 건수가 적음)는 우연에 흔들릴 수 있으니 참고만 한다.
- **한계**: 과거 통계이며 낙찰을 보장하지 않는다. 공사 낙찰 이력만 쓴다(용역은 계산식이 다르다). 복수예비가격 추첨으로 정해지는 예정가격은 개찰 전에는 알 수 없다.

## 12. 개발사업 스마트 법규 검토(law_review) 결과 점검

`/law_review`는 사업 개요·편입 필지(브이월드 지역지구)를 넣으면 AI가 인허가와 단계별 의무를 만든다. AI 결과를 그대로 쓰지 않고 `law_review_verify.py`가 아래 순서로 점검해 보고서(`report.html`) 상단에 요약과 항목별 배지로 보여 준다.

- **입력 단계**: 필지 검증은 브라우저가 브이월드를 직접 호출한다. 조회가 실패한 필지(표의 [API 오류])가 있으면 분석을 막는다(오류 문구가 지역지구로 AI에 들어가 결과가 틀어졌다). 서버에서도 오류 문구는 지역지구로 취급하지 않고 보고서 경고에 적는다. 농지·산지는 필지의 **지목**(전·답·과수원 / 임야)과 정확한 지역지구 이름(농업진흥구역, 보전산지 …)으로 판단한다(예전에는 '전' 글자 포함 검사라 "준보전산지"를 농지로 오인).
- **룰 엔진(`rule_engine.py`, `law_knowledge_base.json`)**: 모르는 변수는 "값 모름"이라 어떤 비교도 거짓이다(예전에는 0으로 읽어 `distance_to_school_m <= 4` 같은 조건이 변수 없이도 참이 되어 모든 사업에 교육시설 안전성평가·예비준공검사·공원사업 시행이 붙었다). 조건에 쓰인 변수를 하나도 모르면 그 규칙은 해당하지 않는다. 조건 `True`인 규칙만 항상 적용된다. 새 규칙을 넣을 때는 조건 변수가 사용자 입력(예산·면적·필지·지목)이나 추출기 변수에서 실제로 채워지는지 확인한다. 편입 필지가 있으면 `has_parcels`가 참이다(토지조서·물건조서/보상계획 공고/협의 규칙).
- **점검 순서(`postprocess`)**: ① 토목·조경 공사에서 건축 법령 항목과 건축 분야 룰을 뺀다(보고서의 "제외한 항목"에 이유와 함께 남는다) ② 조건이 맞는 룰 항목이 결과에 없으면 "＋ 룰 엔진 보완"으로 덧붙인다(해당 조건을 함께 표시) ③ 인용 조문을 법제처 원문과 대조한다(`citation_check`의 로더·판정기 재사용).
- **배지 읽는 법**: ✓ 원문 확인(실제 조문 제목 표시) / ? 확인 필요(조문은 있으나 이 항목의 직접 근거인지 불확실: 제목이 항목과 다른 행위를 다루거나 정의·원칙 조항; 가벼운 표시, 맞는 인용이 섞일 수 있음) / ⚠ 내용 불일치 의심(주제가 다른 분야) / ✕ 조문 없음·삭제된 조문 / · 원문 대조 불가(법령을 못 가져오거나 별표·조례 인용) / ＋ 룰 엔진 보완. 모두 자동으로 지우지 않고 사람이 원문을 확인한다. 판정기는 `law_review_verify.strict_judge`(fit/weak/off 세 단계, 기존 `citation_check._judge`는 명백히 다른 분야만 잡아 제목이 어긋난 인용을 놓쳤다). 조문을 여럿 인용한 항목은 조문마다 판정해 **하나라도 맞으면 일치**, 전부 off면 불일치 의심, 섞이면 확인 필요. 판정이 실패하거나 모르겠다는 답이면 일치로 둔다(근거 없이 의심하지 않음).
- **AI 내용 대조가 실패하면**: 판정 호출은 한 번 다시 시도하고, 그래도 실패하면 해당 항목은 일치로 두되 보고서 상단에 빨간 경고("AI 내용 대조가 N회 실패(사유) … '원문 확인'은 내용이 맞다는 뜻이 아닙니다")가 나온다. 경고 없이 "확인 필요"·"불일치 의심"이 0건이어도 정말 문제가 없는 것인지는 같은 결과를 로컬에서 다시 판정해 비교할 수 있다(2026-11-10 운영 실행에서 판정이 조용히 실패한 정황이 있었다). 사유는 서버 로그 `[law_review_verify] 엄격 판정 호출 실패`에 남는다.
- **주 AI 응답 해석**: AI가 JSON 앞뒤에 설명 글을 붙이거나 형식을 깨뜨리면(운영에서 두 번 중 한 번 "AI가 반환한 데이터를 파싱할 수 없습니다") 바깥 글을 걷어 내고 해석하며, 그래도 안 되면 한 번 더 생성한다(`parse_law_review_json`, 최대 2회). 로그 `[법규 검토] AI 응답을 JSON으로 해석하지 못했습니다`.
- **소요 시간·실패 처리**: 분석 약 3~4분(AI 약 2.5분 + 원문 대조 20~40초). 화면은 최대 8분 기다린다. 점검 한 단계가 실패해도 AI 결과는 그대로 나오고, 보고서에 "일부 점검 단계가 실패했다"고 표시된다(`verification.steps_failed`). 로그: `[law_review_verify] …`.
- **확인 절차(배포 후)**: 샘플(남해읍 도시계획도로, 토목공사, 필지 2개)로 분석 → 보고서 상단에 "법령 원문 대조 결과"가 나오고, 교육시설 안전성평가·예비준공검사가 사라졌으며, 인용이 부적절한 항목에 ⚠ 표시가 붙으면 정상. 시험: `python test_rule_engine.py`, `python test_law_review_verify.py`.
- **한계**: "내용 불일치 의심"은 AI 판정이라 맞는 인용이 의심으로 표시될 수 있고(지방계약법 제17조·제18조 같은 복수 인용은 보완했다), 놓칠 수도 있다. 룰 엔진 보완 항목은 지식 기반 조건에 해당한 항목이라 사업과 관련이 약할 수 있으니 표시된 조건을 보고 판단한다. 지식 기반의 `law_link`는 자유 문장이라 룰 항목의 조문은 원문 대조하지 않는다.

### 12-1. 입력 화면·보고서 도우미 (2026-11-10)

- **저장 위치**: 저장된 분석·작성 중 내용·점검 체크·메모는 **사용자 브라우저의 localStorage에만** 있다(서버에는 올라가지 않는다). 다른 컴퓨터·브라우저·시크릿 창에서는 보이지 않고, 브라우저 사이트 데이터를 지우면 사라진다. 분석 기록은 최근 10건까지 보관(넘으면 가장 오래된 것부터 삭제). 코드: `static/law_review_store.js`(저장 모듈), `static/law_review_input.js`(입력 도우미), `static/script.js`(폼·필지·분석 흐름, `window.LRForm`으로 도우미에 함수 공개).
- **저장된 분석 다시 열기**: `/report?rec=<기록 id>`. 처음 열 때의 **실무 점검 목록(서버가 AI로 걸러 내는 부분)도 기록에 함께 저장**해 다시 열어도 같은 목록·같은 체크가 나온다.
- **주소 붙여넣기**: 한 줄에 주소 하나(앞의 번호·글머리 기호는 자동 제거). 면적은 주소 뒤에 쉼표(`주소, 500`) 또는 탭. 이미 있는 주소는 건너뛰고, 추가하면 자동으로 일괄 검증한다. 필지 검증(브이월드 조회)은 브라우저가 직접 호출한다.
- **필지 요약**: 검증 완료 / 지역지구 조회 오류 / 검증 실패 / 검증 전 개수와 [실패·오류 필지만 다시 검증]·[실패한 필지 삭제]. 지역지구 조회 오류가 있는 필지는 분석을 막는다.
- **진행 표시**: 서버가 `/api/analyze/status/<id>`의 `stage`로 실제 단계(입력 정리 -> 조건 추출 -> 법령 원문 조회 -> AI 분석 -> 링크 -> 원문 대조)를 알리고 화면이 경과 시간과 함께 보여 준다(`app.py`의 `_lr_stage`). 시간 추정이 아니다.
- **오류 안내**: AI 응답 형식 오류, 서버 재시작(배포 직후), 호출 한도, 연결 끊김 등을 원인과 대처가 보이는 말로 바꾸고 [같은 입력으로 다시 시도]를 준다(`LRInput.explain`).
- **보고서**: 엑셀(CSV, UTF-8 BOM, 열: 단계·구분·항목·내용·법적 근거·원문 대조·대조 메모·실무 메모·점검 완료·내 메모), 인쇄/PDF(체크·배지 색 유지, 표 머리글 반복), 점검 체크·메모.

### 12-2. 검토 범위와 룰 엔진 입력 (2026-11-10)

- **입력에서 확정되는 변수**(`lr_flags.derive_flags`): `total_budget`(억 원), `total_project_cost`(원), `total_area_sqm`/`land_area`/`development_area`, `location_type='county'`(필지가 모두 군 지역일 때), `facility_type`('road'/'river'), `has_road_excavation`(도로·굴착·매설 말이 함께 있을 때), `has_parcels`. 지식 기반 규칙이 같은 뜻의 변수를 이름·단위가 다르게 써서 AI 추출기가 짐작해 채우면 발동이 불안정했다(남해군 중기지방재정계획·투자심사 등). 공사비·계약금액·굴착 깊이처럼 입력에서 모르는 값은 만들지 않는다.
- **새 규칙 4개**(조문 제목·본문을 법제처 원문으로 확인): `LAND_OBSTRUCTION_COMPENSATION`(공익사업법 제75조, 편입 필지가 있을 때), `ROAD_EXCAVATION_PLAN`(도로법 시행령 제56·59·60·61조, 도로 굴착 사업일 때), `CONTRACT_SUPERVISION`(지방계약법 제16조·시행령 제56조), `DEFECT_WARRANTY_INSPECTION`(지방계약법 제21조·시행령 제70·71조, 유지관리 단계). 규칙의 `phase`는 planning/design/construction/completion/maintenance를 쓸 수 있다.
- **중복 정리**: AI 항목과 룰 항목이 이름만 다르게 쓴 것(기본구상용역 / 기본구상 및 기본계획 수립 등)을 이름 유사도(글자 두 개씩 겹침 0.72 이상) 또는 같은 조문 인용 + 이름 유사도 0.35 이상으로 합친다. 서로 다른 규칙을 합쳐 누락시키는 것보다 중복이 낫다는 원칙이라 기준을 높게 잡았다. 건축 분야 룰 제외는 "건축물·입목·공작물"처럼 물건 나열의 '건축물'은 건축 사업으로 보지 않는다.
- **하지 않은 것**: 남해군·경상남도 조례·규칙을 새로 추가하지 않았다(조문 원문을 확인하지 않은 조례를 넣으면 틀릴 위험). 새로 넣을 조례는 이름을 알려 주면 조문을 확인해 추가한다.
- **시험**: `python test_lr_flags.py`, `python test_law_review_page.py`, `python test_law_review_verify.py`.
