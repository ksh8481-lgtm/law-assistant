# PDF 요약본 도구 `tools/pdf_digest.py` (2026-11-14)

## 문제
글자·표·그림이 섞인 PDF를 AI에 통째로 보내면(쪽 전체를 이미지로) 토큰이 많이 든다. 쪽마다, 한 쪽 안에서도 부분마다 성격이 다르다.
pymupdf / markitdown / pymupdf4llm 중 하나만 쓰면 한 종류에만 맞는다.

## 시험으로 확인한 것 (감정평가서 스캔본 8쪽, 사용자 PDF)
- pymupdf·markitdown·pymupdf4llm **모두 0자**(스캔본이라 글자 정보가 없음). 이 도구들은 글자가 선택되는 PDF에서만 의미가 있다.
- Windows 내장 한글 OCR: 8쪽 약 3초, 무료, 설치 불필요. 줄글은 대체로 맞지만 오인식이 있고("창선"->"장선", "상대우체국"->"상대우제국", 하이픈 소실),
  **표는 칸 순서가 깨진다**("(1F)"->"(IF)", "1,800,000"->"1 ,800,000"). 금액·이름은 이미지로 확인해야 한다.
- 같은 방식으로 글꼴 매핑이 없어 글자가 기호로만 나오는 PDF(브라우저 인쇄본)도 OCR 로 읽혔다("garbled" 쪽).
- 토큰 어림(글자 수/1.3, 이미지 가로x세로/750 - 실측 아님): 쪽 전체를 이미지로 10,312 -> 요약본 글자 2,475 + 표 쪽 이미지 1,615 = 약 4,090(약 60% 절감).

## 도구가 하는 일
쪽마다 분류: `digital`(글자 있음) / `scan`(글자 거의 없고 이미지) / `garbled`(글자가 기호뿐). 결과: `digest.md` + `figs/*.png` + `summary.json`.
- digital: 글자 + **선이 있는 표는 마크다운 표**(pymupdf `find_tables`; 표 안 글자는 본문에서 뺌) + **그림은 잘라서 낮은 해상도 PNG**(벡터 차트·도면은 `cluster_drawings`, 래스터는 이미지 영역;
  축 눈금 같은 짧은 글자는 그림에 포함, 그 글자는 그림 아래 한 줄로도 남김) + 본문에는 자리표시자만. 캡션("그림 1." 등)은 그림 옆에 붙인다.
- scan/garbled: OCR 글자 + 쪽 이미지(필요할 때 확인용). OCR 글자 모양이 표 같으면(줄이 20개 이상, 평균 9자 이하) "표로 보임 - 이미지 확인" 표시.
- AI 는 `digest.md` 만 읽고, 그림은 필요한 것만 열어 본다(느리게 읽기). 쪽 전체를 이미지로 보낼 때와의 절감 어림을 출력한다.

## 선택과 근거
- 세 도구를 모두 돌려 비교하지 않고 **쪽별로 규칙으로 하나를 고른다**(빠르고 비용이 없다). 외부 패키지는 pymupdf 하나만 쓴다(서버 요구사항에 이미 있음).
  markitdown/pymupdf4llm/docling 은 필요 없었다: 글자 추출은 pymupdf 로 충분했고, 표는 pymupdf 가 선 있는 표를 처리하며, 스캔본에는 어느 것도 못 쓴다.
- 스캔본의 표 판별: 이미지의 가로·세로선을 세는 방식은 스캔의 회색 선·기울기 때문에 불안정해서 버렸다(표 쪽 5쪽을 못 찾음). OCR 글자의 줄 길이로 판단한다.

## 한계
- 이 컴퓨터(Windows)용 OCR 이다. 그 밖의 환경에서는 OCR 없이 쪽 이미지만 만든다(서버의 스캔본은 기존처럼 Gemini 에 파일째 보내는 방식 유지).
- 선 없는 표는 못 찾는다(글자로 나옴). 단이 여러 개인 쪽은 읽는 순서가 틀릴 수 있다. 표 판별 기준(줄 길이)은 한 문서로 맞춘 값이다.
- 토큰 절감은 어림값이다. 실제 사용량은 같은 문서로 비교해 확인한다.

## 사용법
`python tools/pdf_digest.py 문서.pdf [-o 출력폴더] [--pages 3-9] [--dpi 80] [--no-ocr]`, 시험: `python test_pdf_digest.py`(16개, OCR 시험은 Windows 에서만).
